# Steam Software판 UTF-8 지원 조사 — 2026-10-13

사용자의 마지막 지시에 따라 번역 검수보다 게임 UTF-8 지원 조사를 우선했다. 번역 검수 진행률은 400/4,866건에서 변경하지 않았으며 번역 초안·원본·진행 JSON을 수정하지 않았다.

## 실제 실행 파일에서 확인한 제약

`RG.EXE`는 MZ 스텁 뒤에 LE 이미지를 가진 32비트 실행 파일이다. 확인한 파일 크기는 4,241,144바이트, LE 헤더 파일 위치는 `0x3178`이다. 아래 주소는 **LE 오브젝트의 preferred base 기준**으로, 재배치 이후의 실제 실행 주소로 단정하면 안 된다. `output/engine_utf8/engine_utf8_report.json`에 SHA-256 및 정확한 파일 위치를 기록했다.

| 위치 | 확인한 동작 | UTF-8 지원에 필요한 변경 |
| --- | --- | --- |
| `0x187F8` 함수, `0x1880E` 명령 | `mov al, byte ptr [edx]`로 문자 1바이트를 읽고 폰트 시작 코드를 뺀다. 조건에 따라 대소문자 변환 호출도 존재한다. | 코드포인트 디코딩, 소비 바이트 수 처리, ASCII에 한정한 대소문자 변환 검토 |
| `0x76E98` 함수 | 텍스트 길이를 구한 뒤 그리기 루프에서 `0x76F61`의 포인터 증가를 한 바이트씩 수행한다. | 디코딩 결과에 따라 문자 포인터와 반복 조건을 함께 변경 |
| `0x77185` 함수 | 너비 계산에서도 `0x771CB`에서 포인터를 한 바이트씩 증가하고 동일 문자 해석 함수를 호출한다. | 그리기와 동일한 코드포인트·너비 계산 적용 |
| `0xA731B` 함수 | FNHD·FBMP 처리 및 비트맵 적재. `0xA7569`에서 개수를 `0x100`과 비교하고 `0xA7574`에서 최대 256으로 제한한다. | 개수 필드만 바꾸지 말고 저장 구조 전체 교체 |

폰트 메모리 구조에는 `active` (`+0x50`), `xsize` (`+0x250`), `ysize` (`+0x450`), `xco` (`+0x650`), `yco` (`+0x850`), `data` (`+0xA50`) 테이블이 있다. 실행 파일에 남아 있는 해당 필드명 문자열과 로더/그리기 명령을 함께 확인했다. 각 16비트 배열 간 간격은 `0x200`이므로 256개를 넘기면 다음 필드를 침범한다. 로더는 `0xE50` 크기의 구조를 사용한다. **256 제한 비교 명령만 제거하는 패치는 불충분하다.**

현 번역 4,866건에는 고유 한글 음절 **994종**, 전체 고유 문자 **1,059종**이 있다. 단일 256글리프 테이블에 그대로 넣을 수 없다. 최장 번역은 UTF-8 기준 919바이트다. 이 값이 실제 엔진 버퍼에 들어간다는 검증은 아직 없다.

## 재현 도구와 결과

```powershell
python tools/encoding/inspect_utf8_engine.py --exe 'C:\Games\Steam\steamapps\common\The Elder Scrolls Adventures Redguard\Redguard\RG.EXE'
```

`capstone`이 필요하다. 도구는 LE 페이지 맵을 통해 명령 위치를 계산하고 5개 명령 시그니처를 검증한다. 다른 실행 파일이면 불일치 오류로 중단한다. 실행 파일의 재배치 fixup은 적용하지 않으며 패치 기능은 없다. 설치 파일은 읽기만 한다. 분석 전후 실행 파일 해시 일치도 확인한다.

출력은 `output/engine_utf8/`에 저장한다. `byte_to_glyph.asm.txt`, `draw_text.asm.txt`, `measure_text.asm.txt`, `font_loader.asm.txt`에는 함수 단위 역어셈블을 저장한다. 게임 기계어와 원문이 포함될 수 있는 분석 결과는 공개 Git에서 제외한다.

## 아직 남은 구현

1. 문자 디코더의 모든 호출 지점과 문자열 길이·복사·줄바꿈·수명 계산 경로 추적.
2. 고정 폰트 구조 대신 사용할 유니코드 글리프 저장 구조와 기존 ASCII 호환 경로 설계.
3. UTF-8 디코딩, 문자별 포인터 이동, 그리기·너비 계산을 함께 구현.
4. DOS 호출 규약, 세그먼트 주소, LE fixup을 반영한 후킹 코드 및 테스트 복제본 구성.
5. 실제 화면에서 자막·HUD·메뉴 출력 검증. 이번 조사에서는 게임을 실행하지 않았다.

**현재는 원인을 실행 파일에서 확인한 단계이며, 게임 UTF-8 지원을 구현한 상태가 아니다.** UTF-8 RTX를 생성하는 것만으로 이 엔진 경로가 바뀌지 않는다.

LE 구조 정의 참조: [Open Watcom exeflat.h](https://github.com/open-watcom/open-watcom-v2/blob/master/bld/watcom/h/exeflat.h). 자막·HUD의 외부 조사 자료는 Glide판이므로 위 Software판 주소의 근거로 사용하지 않았다.
