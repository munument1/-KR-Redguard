# 유니코드 글리프 테이블·줄바꿈 코어 구현 — 2026-10-13

## 결과와 적용 범위

고정 256개 FNT 배열을 대체하기 위한 **별도 유니코드 폰트 포맷과 x86 조회·줄바꿈 코어**를 구현했다. 실제 `RG.EXE`의 로더·그리기 함수에는 아직 연결하지 않았다. 원본 실행 파일에서 256 제한이 해제됐다는 뜻이 아니다.

기존의 256 비교 명령을 제거하는 대신 별도 저장 구조를 사용한다. 기존 구조의 16비트 배열 여섯 개를 그대로 확장하면 인접 필드를 덮어쓰기 때문이다. 앞으로 로더·그리기·해제의 모든 사용처를 새 구조로 연결해야 한다. 이번 작업은 해당 연결에 사용할 코어를 실제 x86 기계어로 작성하고 에뮬레이터에서 검사한 단계다.

## 글리프 저장과 조회

`tools/encoding/unicode_font.py`가 `KGF1` 팩을 작성·검증한다. 이 파일은 원본 FNT의 호환 확장 포맷이 아니며, 새 로더가 필요하다.

- 유니코드 scalar를 키로 정렬한 희소 테이블이다. 바이트 값이나 `문자 - 시작 코드`를 배열 첨자로 사용하지 않는다.
- 글리프 개수와 주소는 32비트 필드다. 현재 검증기는 자원 제한을 위해 최대 65,535개를 허용한다.
- 24바이트 레코드마다 코드포인트, 비트맵의 상대 위치, 크기, 원점, 전진 폭, 활성 여부 및 비트맵 길이를 저장한다.
- `unpack`은 순서, 중복, surrogate, 길이, 비트맵 범위와 정규 형식을 확인한다. x86 조회 함수는 **이미 검증된 팩**을 입력으로 받는다.
- x86 이진 검색은 8비트 슬롯을 사용하지 않는다. 3,000글리프 팩의 저장 왕복 및 256번 이후 한글의 실제 x86 조회를 검사했다.

현재 번역용 개발 팩은 원본 REDSEL의 기존 글리프와 개발용 Noto Sans KR 20px를 합친 **1,206글리프, 387,770바이트**다. KimDaeGeon 글꼴은 사용하지 않았다. Noto Sans KR은 시험용 선택이며 최종 인게임 서체를 확정한 것이 아니다. 폰트 cmap을 검사해 없는 문자를 무조건 tofu로 받아들이지 않는다. 잘못된 UTF-8의 U+FFFD는 명시적으로 원본 `?` 비트맵으로 대체한다.

## 줄바꿈

`tools/encoding/unicode_layout_x86.py`는 디코더·희소 조회·줄바꿈을 하나의 주소 독립적인 32비트 x86 바이너리로 조립한다. 현재 바이너리 크기는 851바이트다. 코드 내부 호출만 사용하며 외부 함수를 호출하지 않는다.

입력은 문자열 포인터, **바이트 길이**, 검증된 폰트 팩, 최대 픽셀 폭, 출력 배열, 출력 개수 한도다. 결과 레코드는 `start`, `end` 바이트 위치와 픽셀 너비, 상태 플래그다. 원문 버퍼를 수정하지 않는다.

- 문자마다 UTF-8 소비 바이트 수만큼 이동한다. 2·3·4바이트 문자의 중간을 줄 경계로 반환하지 않는다.
- 너비는 그 문자의 글리프 전진 폭으로 합산한다. 활성화되지 않은 글리프는 0폭, 없는 글리프는 `?`로 계산한다.
- 가능한 경우 공백에서 끊고, 공백 없는 긴 단어·한글은 코드포인트 경계에서 끊는다. 줄 경계 공백·탭 일부는 화면에 출력하지 않는다.
- CR, LF, CRLF를 처리하고 명시적인 빈 줄을 유지한다. 탭은 공백 폭의 4배다.
- 글리프 하나가 제한 폭보다 크면 단독 행으로 반환하고 초과 플래그를 설정한다. 무한 반복하지 않는다.
- 출력 개수 초과와 잘못된 최대 폭을 상태 코드로 반환한다. 출력 배열을 넘어 쓰지 않는다.

남은 품질 과제도 있다. 현재 경계는 유니코드 코드포인트 기준으로, 결합 문자·ZWJ 이모지 같은 grapheme이나 한국어 금칙 문장부호 규칙은 구현하지 않았다. 원본 게임의 strict `<` 토큰 규칙과 달리 새 코어는 폭이 제한과 같으면 허용한다. 기존 영문과 화면 배치를 비교해 최종 정책을 결정해야 한다.

## 검사

```powershell
python tools/encoding/unicode_layout_x86.py
python tools/encoding/check_unicode_corpus.py --legacy-font 'C:\Games\Steam\steamapps\common\The Elder Scrolls Adventures Redguard\Redguard\fonts\REDSEL.FNT' --development-font 'C:\Windows\Fonts\NotoSansKR-Regular.ttf'
python -m unittest discover -s tests -v
```

폰트 생성에는 Pillow와 fontTools, x86 실행에는 앞서 준비한 로컬 Keystone·Unicorn이 필요하다.

전체 번역 **4,866건**을 실제 x86 코드로 실행했다. 500px 한도에서 글자 누락·중복, 잘못된 UTF-8 경계, 비트맵 메트릭과 너비의 차이 및 폭 초과가 없었다. 가장 긴 출력은 14줄이다. 번역 초안의 작업 전후 SHA-256도 일치했다. 이 검사는 자막의 화면 위치, 음성과의 동기화, 실제 비디오 메모리 출력을 확인한 검사가 아니다.

전체 자동 테스트 **40개 통과**. 추가 검사에는 혼합 문자열 100개에 대한 글자 보존·실제 너비 대조, 출력 버퍼 끝의 미매핑 페이지, 잘린 UTF-8, 누락된 글리프, 비활성 글리프 및 레지스터·스택 보존 검사가 포함된다.

## 다음 통합 지점

실제 설치본에서 폰트 로더 `0xA731B`, 그리기 `0x76E98`, 너비 계산 `0x77185` 및 기타 텍스트 경로가 구형 구조를 사용한다. 이 주소는 LE preferred address이며 런타임 재배치 주소가 아니다. 새 팩의 로더·수명 관리를 구현하고 그리기 코드가 24바이트 레코드와 상대 비트맵 위치를 사용하게 연결해야 한다. 자막 분할 결과는 원문 바이트 범위이므로 기존 NUL 종료 문자열 인터페이스로 전달하는 어댑터도 필요하다.

KGF1 파일을 게임 폴더에 복사하거나 기존 FNT 대신 이름만 바꾸는 것으로 적용할 수 없다. DOS/LE 후킹·세그먼트 및 fixup, 각 UI 경로의 버퍼 검증과 실제 게임 검사가 끝난 후에만 배포 패처의 게임용 매니페스트를 생성한다.

## 반복 순회·시험 문구 재출력 확인

사용자가 배틀스파이어에서 겪었던 성능 문제를 레드가드에서도 확인하도록 요청했다. 현재 레드가드 작업물에는 11,413슬롯으로 확장한 실행 파일이나 게임에 연결된 폰트 선택/그리기 후크가 없다. 원본 RG.EXE의 해시도 조사 당시와 일치한다. 따라서 실제 게임 후크가 이 문제를 일으키지 않는다고 검증한 단계는 아니다.

현재 코어의 글리프 조회는 이진 검색이다. `test_lookup_does_not_scan_11413_slots`에서 11,413레코드 테이블을 구성하고 모든 키 및 양쪽 범위 밖 키를 x86 에뮬레이터로 조회했다. 메모리 읽기 후크로 비교한 레코드 수를 집계했으며 **각 조회에서 최대 14레코드**였다. 전체 슬롯을 순회하지 않았다. 해당 파일의 테스트 11개가 통과했다.

`unicode_layout_x86.py`는 줄의 바이트 범위와 픽셀 너비만 반환하며 비트맵을 그리지 않는다. 시험 문구는 `preview_korean_font.py`의 `main()` 안에서 오프라인 PNG 생성 시에만 그린다. 현재 런타임 코드에서 이 도구를 호출하는 경로는 없다.

게임에 연결할 때 유지할 조건:

- 행 높이와 기본 폰트 메트릭은 로드 시 계산·보관하고, 폰트 선택 시에는 저장된 값을 읽는다. 크기별 폰트는 별도 메트릭을 가진다. 폰트를 새로 로드하거나 교체할 때만 갱신한다.
- 글자 출력 함수에서 폰트 전체를 재검증하거나 높이를 다시 계산하지 않는다. KGF1 전수 검증은 로드 시 한 번 수행한다.
- 시험 문구는 일반 문자 출력 함수에 넣지 않는다. 진단 화면이 필요하면 기본적으로 꺼진 별도 경로로만 실행한다.
- 실제 후크가 완성되면 폰트 선택 반복, 문자열 출력 길이에 따른 호출 수를 계측한다. 현재의 조회 테스트만으로 폰트 선택·그리기 비용 검증을 대신하지 않는다.
