# 한국어 인코딩 및 렌더링 설계

| 방식 | 가능성 | 필요한 엔진 변경 | 현실적 제약 |
|---|---|---|---|
| A. 완성형 음절 FNT 확장 | 파일 포맷상 기록 연구 가능 | 2바이트 문자 디코딩, 확장 글리프 인덱스·메모리·폭 계산 | 원본 엔진 256글리프 한계, 실제 번역의 음절 종류 미정 |
| B. 자모 합성 | 연구 가치 높음 | 초중종성으로 해석, 겹치기 그리기, **음절당 1번 전진**, 합성 폭·줄바꿈 변경 | 조합별 글리프 모양과 자막 스타일 구현 난이도 |
| C. 별도 한글 렌더러 | 장기적으로 가장 유연 | 게임 문자열·자막·메뉴 경로 후킹, 독립 글꼴 렌더링 | DOS/4GW 메모리·Software/Glide 전용 경로 파악 필요 |

## 임시 권장 순서

1. **한 바이트 치환으로 1글자 출력**을 먼저 검증. 여기는 2바이트 파서/새 버퍼가 필요 없어 원인을 분리할 수 있습니다.
2. 포맷용 번역 원본은 UTF-8 JSON으로 관리. 게임에는 별도 명시한 바이트 인코딩으로만 내보냅니다.
3. 한글 문장이 확보되면 실제 사용한 유니코드 음절 종류와 초성(19)·중성(21)·종성(27종) 종류 수를 조사해 A와 B의 메모리/구현 부담 비교.
4. 게임이 2바이트 처리를 지원하도록 수정할 수 있으면 A(완성형 매핑) 또는 B(자모 합성) 중 더 검증 가능하고 부담이 적은 방법을 선택합니다. 두 방법 모두 텍스트 버퍼 안전성을 확인해야 합니다.
5. 언어별 개별 렌더 경로가 너무 많거나 버퍼/폰트 확장이 불가능하면 C로 전환.

**CP949는 후보일 뿐입니다.** 2바이트 값이 FNT 인덱스로 처리된다는 증거가 없으므로 `--codec cp949` 결과를 인게임에 투입하지 않습니다. UTF-8 역시 원본 엔진에서 직접 사용할 수 있다는 근거가 없습니다.

오픈 라이선스 글꼴로는 [Noto Sans KR](https://github.com/notofonts/noto-cjk)(SIL OFL 1.1) 등을 검토할 수 있습니다. 구체 파일 배포 여부는 라이선스 전문과 배포 조건을 확인한 뒤 결정합니다. 저장소에 글꼴 파일은 포함하지 않습니다.
